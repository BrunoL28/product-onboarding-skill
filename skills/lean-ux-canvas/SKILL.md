## Purpose
Guide teams through creating Jeff Gothelf's Lean UX Canvas (v2)—a one-page tool that frames work around a **business problem to solve**, not a **solution to implement**. Use this to align cross-functional teams around core assumptions, craft testable hypotheses, and ensure learning happens every sprint.

It's an "insurance policy" that turns assumptions into experiments before committing to full development, shifting conversations from outputs to outcomes.

## Canvas Structure (8 boxes, fill in this order)
1. **Business Problem** — what changed in the world that created a problem worth solving?
2. **Business Outcomes** — measurable behavior change that indicates success (metrics).
3. **Users** — which persona(s) to focus on first.
4. **User Outcomes & Benefits** — why users would seek this; the benefit/emotion (empathy).
5. **Solutions** — features/initiatives that might solve the problem (hypotheses, not commitments).
6. **Hypotheses** — "We believe [outcome] will be achieved if [user] attains [benefit] with [solution]." One solution each.
7. **What's most important to learn first?** — the single riskiest assumption right now (value/usability/feasibility/viability).
8. **What's the least work to learn next?** — smallest experiment to validate/invalidate it.

**Key distinction:** Box 2 = metrics (behavior change); Box 4 = human benefits/emotions.

### Anti-Patterns
Not a feature list; not a project plan; not a replacement for strategy; not a one-time exercise.

## Application
Walk through 8 adaptive questions (one per box) in sequence, offering guidance, examples, and options. Gather business + user context first. For each box, validate quality before moving on. Then review/export the canvas and iterate Box 7 → Box 8 until confidence is high enough to build.

## Common Pitfalls
1. Starting with solutions, not problems.
2. Vague business outcomes.
3. Too-broad user segments.
4. Confusing Box 2 (metrics) and Box 4 (empathy).
5. Only one solution in Box 5.
6. Skipping experiments (Box 8).
